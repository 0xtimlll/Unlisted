# Unlisted — контекст для новой сессии

Приватный некастодиальный мост. Next.js static export на Cloudflare Pages, только desktop.
Вкладки: OFT (LayerZero), NTT (Wormhole), CCIP (Chainlink), Rescue. Мост определяется из адреса
токена, а не выбирается пользователем.

## Четыре правила, которые старше любой задачи

1. **Безопасность средств — приоритет №1.** Никаких unlimited approve. Никаких адресов протокольных
   контрактов из пользовательского ввода или внешних API в рантайме без сверки — только из
   закоммиченного конфига, проверенного on-chain.

   Уточнение, которого правилу не хватало: **внешний API может только сужать поиск, но никогда —
   повышать доверие.** Ответ стороннего сервиса имеет право подсказать, что проверять; решает
   всегда цепочка on-chain фактов, закреплённая адресом из закоммиченного конфига. Отсюда следует
   и обратное: отсутствие в чужом каталоге — не отказ. Список NTT-токенов с `api.wormholescan.io`
   был проверкой №1 в гейте `wormhole-ntt/verify.ts` и перестал ею быть: теперь гейт — это
   `minter()`/`MINTER_ROLE` у самого токена, peers в обе стороны и transceiver, указывающий на
   `coreBridge` **из нашего конфига**. Недоступность каталога не должна останавливать ни поиск,
   ни отправку.
2. **Сервис информирует — решает человек. Никаких галочек.** Unlisted нужен для арбитража, и
   отказ строить транзакцию из-за мнения о чужом контракте делает инструмент бесполезным ровно на
   тех маршрутах, ради которых он существует. Процесс простой: Approve → Send. Кнопка неактивна
   **только когда транзакция физически не пройдёт**: нет кошелька или не та сеть, нет баланса
   токена или нативного газа, нет маршрута (peer / trustedRemote / менеджер не верифицирован),
   сумма после dust и комиссии равна нулю, адрес получателя невозможно закодировать для VM сети
   назначения. Такая причина показывается одной нейтральной строкой под кнопкой с действием
   («пополните газ», «увеличьте сумму»), без красных блоков. Таблица блоков —
   `src/core/severity.ts`; добавляя код, спрашивать надо ровно одно: «транзакция невозможна?».

   **Всё остальное — не блок, а цвет индикатора** (`src/core/indicator.ts`): нулевой адрес,
   получатель = контракт маршрута, адрес-двойник, peer не указывает обратно, dead DVN, NTT без
   якоря — красный с одной видимой строкой; свежий адаптер, один RPC, упавшая симуляция, слабый
   DVN-набор, комиссия выше потолка — жёлтый; прокси и владелец-EOA — только строка в подробностях.
   Индикатор ничего не запрещает и не ограничивает сумму. Галочек, «тестового лимита», баннеров
   «cannot be sent» / «route unverified» / «issues to fix» нет и не должно появиться. Подтверждение
   последних 6 символов нового или импортированного адреса остаётся — это ввод, а не галочка.

   **Инварианты сборки транзакции блокируют всегда**, но не показываются как ограничения: calldata
   только через `abi + functionName + args`, approve строго на точную сумму (единственное
   исключение — approve(0) перед approve(сумма) для токенов вроде USDT, которые ревертят смену
   ненулевого allowance; итоговый allowance всё равно ровно сумма), spender — контракт маршрута,
   прошедший верификацию, никакого approve при `approvalRequired === false`, `refundAddress` —
   подключённый кошелёк, кодировка получателя ровно та, которой его прочтёт destination. Это не
   суждение о чужом контракте, а корректность самого сервиса: если такой код сработал — это баг.

3. **Что может дать зелёный цвет.** Зелёный даёт только факт, который атакующий **не может
   написать сам о себе**: права или настройки контракта, который он не контролирует (настоящий
   токен на исходной сети, реестр протокола, `EndpointV2`), либо деньги и история, которые
   стоят реальных средств (доля supply, залоченная в адаптере, и число отправок по данным
   endpoint'а). Закоммиченных списков адаптеров и locking-хабов больше нет — цвет от них не
   зависит. Утверждения контрактов, до которых мы дошли **по цепочке от проверяемого контракта**
   (`peers`, `token()` фейкового менеджера, ответы transceiver'а и т.п.), доверие не повышают
   никогда — вся эта цепочка принадлежит тому, кого мы проверяем.

   Так была устроена дыра в NTT: якорь со стороны назначения (`dstToken.minter() == dstManager`)
   заменял якорь со стороны источника, а до назначения мы доходили через `manager.getPeer()` —
   то есть через утверждение самого проверяемого менеджера. Фейковый менеджер для настоящего USDC
   проходил гейт, потому что вторую половину пары атакующий писал сам. Правило выше — обобщение
   этого случая: **`token()` у менеджера — заявка, `minter()` у настоящего токена — факт.**

4. **Ничего не выдумывать.** Адреса, ID, ABI, селекторы — только из первоисточников и с проверкой
   через RPC. Селектор, посчитанный по памяти, даёт `REVERT` на живом контракте и выглядит как
   «контракт не поддерживает функцию». Считать из сигнатуры: `toFunctionSelector('function eid()')`.

Не ломать то, что работает: существующие пути отправки OFT v2 / NTT / CCIP не переписывать без
необходимости, новое — отдельными модулями.

**Все отчёты и ответы — на русском.**

## Архитектура

**Реестр сетей** — `src/core/chains.ts`. `ChainDef` — размеченное объединение по `vm`
(`'evm' | 'svm'`). Всё, чему нужен `chainId` или wei, обязано сначала сузиться через `isEvm()`.
У каждой сети есть `feeCeiling` — намеренно щедрый потолок комиссии в наименьшей единице
(guard 21 не отказывает, а просит подтвердить сумму).

**Ядро** — `src/core/`: `probe.ts` (детект OFT), `plan.ts`, `guards.ts`, `severity.ts` (что
держит кнопку), `indicator.ts` (цвет и причины), `approveFlow.ts` (автомат Approve → Send),
`reverse.ts` (разворот маршрута: контракт другой стороны из peer, затем полный probe заново),
`recipient.ts`, `quorum.ts` (кросс-проверка двух RPC), `options.ts`, `verify.ts`, `track.ts`,
`decodeTx.ts`.

**Протокольные модули** — `src/protocols/`:

| Модуль | Что делает |
|---|---|
| `lz-v1/` | LayerZero v1 OFT: три wire-стандарта (`bytes`, `bytes32`, `bytes32_fee`), adapterParams, свой `selfcheck.ts`, 22 guard'а, `send.ts` — единственное место, где уходит `sendFrom` |
| `lz-risk/` | Восемь проверок маршрута (5 жёстких, 4 уровня) — вход для `core/indicator.ts`. Ни одного write-примитива |
| `lz-rescue/` | Вкладка Rescue: четыре действия из белого списка, `keccak256(payload)` сверяется с on-chain хешем |
| `wormhole-ntt/` | NTT |
| `ccip/` | CCIP |
| `src/core/svm/` | Solana (на `@layerzerolabs/oft-v2-solana-sdk`) |

Таблицы, а не хардкод: `lz-v1/chains.json` (v1 chainId, endpoint, ULN, `v1Active` + причина),
`lz-risk/dvns.json` (614 DVN, 94 deprecated). Обе генерируются — см. ниже.

## Правила безопасности

**Белый список** — `scripts/check-whitelist.mjs`, часть `npm test`. Запрещено везде в `src/`:
`eval`, `new Function`, `dangerouslySetInnerHTML`, любые подписи сообщений (`signMessage`,
`signTypedData`, `personal_sign`, `permit`), `sendTransaction` / `sendRawTransaction` (сырой calldata),
`signAllTransactions`, ручная сборка Solana-инструкций, SPL-делегаты и `setAuthority`.

**Scoped-категории**: write-примитив разрешён только в своём модуле — `transfer` в `wormhole-ntt/`,
`ccipSend` в `ccip/`, `sendFrom` в `lz-v1/`, а `retryPayload` / `retryMessage` / `commitVerification` /
`lzReceive` — каждый только в `lz-rescue/`. Отдельно `SIMULATED_ONLY` (`nonblockingLzReceive`,
`lzReceive`): эти имена разрешены как `functionName` внутри `lz-risk/` ради `eth_call`, и сам модуль
отдельно проверяется на отсутствие любого write-примитива.

**Одна кнопка: Connect wallet → Switch to <сеть> → Approve <сумма> <токен> → Send.**
`needs_approve` — единственный блок-«шаг» (`isStepCode` в `severity.ts`): держит `canSend`, но не
считается проблемой. Approve показывается, когда allowance меньше суммы, и активен, когда кроме
allowance ничего не мешает (`waitsOnlyForApprove`); если allowance хватает — сразу Send. Поток
approve — `core/approveFlow.ts` + `ui/useApproveFlow.ts`: симуляция plain approve → (approve(0)
для USDT-подобных, шаги «1/2», «2/2») → подпись → receipt → перечитывание allowance с повторами →
кнопка сама становится Send. Отказ в кошельке — нейтральная строка «Cancelled in the wallet»,
ошибка — короткая причина и «Try again». Смена суммы выше allowance — снова Approve. Одинаково во
всех четырёх вкладках через `components/Review.Cta`.

**Индикатор маршрута** — одна плашка `components/RouteIndicator.tsx`: шарик + подпись, причины в
подсказке при наведении, для красного одна строка видна сразу, всё подробное (8 проверок, список
guard'ов, флаги, DVN, доля адаптера) — в свёрнутом «Details». Серый до выбора сети и до суммы.

**Guard'ы** — `src/core/guards.ts`, 22 штуки, от `g1Chain` до `g22Risk`. Ключевые: `g11NoApprove`
(нет unlimited approve), `g15ExecutorGas`, `g19RecipientVm`, `g20SvmSend` (отказ, если svm-destination не опознан),
`g21FeeCeiling`, `g22Risk`.

**Независимая проверка получателя.** `selfCheck` каждого протокола **не переиспользует функции
кодирования** — это отдельный декодер, читающий адрес ровно так, как его прочтёт контракт на
destination. Для v1: у `bytes` длина обязана быть ровно 20 байт; у `bytes32` старшие 12 байт обязаны
быть нулями. Селектор в calldata обязан соответствовать обнаруженному стандарту, таблица селекторов
вычисляется из сигнатур. Несоответствие — блок, а не предупреждение.

**Симуляция.** Перед подписью — `eth_call` ровно той же транзакции (на V2 — вместе с approve через
`eth_simulateV1`, где нода умеет). Её результат **не блокирует**: гарантированные реверты ловятся
своими блокирующими guard'ами (нет peer'а / trustedRemote, не хватает баланса или allowance, сумма
после dust или комиссии равна нулю, adapterParams не той формы, получатель не той кодировки), а общий
провал симуляции — `simulation_failed` — предупреждение веса `loss` с декодированной причиной реверта
в тексте (`formatRevert`), потому что часто это сбой RPC, а не свойство перевода. Недоступный RPC —
отдельный код `simulation_unavailable`, тоже предупреждение: «не проверено» — не «упадёт».

**Подтверждение получателя.** UI **никогда** не показывает последние символы адреса рядом с полем,
где просит их ввести: значение, выведенное из того же поля, превращает проверку в «умеет ли
пользователь копировать». Подсказка отправляет читать хвост из источника, откуда адрес скопирован.
Одно правило на все вкладки — `core/recipient.confirmsTail()`: регистр игнорируется на EVM (в EIP-55
это контрольная сумма), учитывается на Solana (там регистр — часть адреса).

**Адресная книга** (`core/addressBook.ts`). Три правила, и они держатся guard'ом 3, а не только UI:

- адрес попадает в книгу **только явным действием пользователя** и только после подтверждения
  последних 6 символов. Автосохранения нет нигде; после отправки обновляется лишь `lastUsedAt`
  у записи, которая уже была в книге;
- адрес, точно совпавший с записью, **не требует** повторного подтверждения хвоста — он уже был
  проверен руками один раз;
- адрес, совпавший с записью по первым 4 и последним 4 значащим символам, но **не равный** ей —
  `recipient_lookalike`: красный индикатор с одной видимой строкой «Похож на "…", но это ДРУГОЙ
  адрес». Это форма подмены адреса: подменяют середину, сохраняя края, на которые смотрит человек.
  Отправку не блокирует (правило 2), но книга сама двойников не заводит;
- присутствие двойника **в книге** само по себе красный не снимает. Пара записей с одинаковыми
  краями допустима только если пользователь про эту конкретную пару сказал «да, это другой адрес» —
  в форме добавления или построчно в предпросмотре импорта; ответ записывается на запись
  (`distinctFrom`). Строка импорта с двойником без своего подтверждения **не импортируется**;
  подтверждённая — остаётся `imported` и требует хвост при первом использовании. Двойник, попавший
  в книгу любым другим путём (правленный localStorage), остаётся двойником, и симметрично —
  записи, на которые он похож, пока его не удалят. `distinctFrom` из импортируемого файла
  игнорируется — это утверждение файла, а не пользователя.

Битые данные книги в localStorage — это `corrupt`: показать ошибку, отдать сырую строку пользователю
и **не перезаписывать**. Настройки можно пересобрать из умолчаний, адреса — нельзя.

**Правила индикатора риска** (`lz-risk/risk.ts`). Проверки: `peers`, `path`, `config`, `delivery_sim`,
`adapter_liquidity`, `limits`, `history`, `recent_changes`. Жёсткие — `peers`, `path`, `delivery_sim`,
`adapter_liquidity`, `limits`. Уровни `BLOCKED | UNVERIFIED | CAUTION | OK`. Правила:

- **невыполненная проверка = серая «не проверено» с причиной**, никогда не зелёная галочка;
- у состояния есть разница между `skipped` (не применимо к маршруту) и `unchecked` (не удалось);
- если не выполнилась **жёсткая** проверка — итог не выше `UNVERIFIED`, что бы ни говорили остальные;
- уровень **не запрещает отправку и не ограничивает сумму** — он даёт цвет индикатору
  (`core/indicator.ts`): `BLOCKED` (dead DVN, несовпадение конфигов, провал жёсткой проверки) →
  красный, `UNVERIFIED` / `CAUTION` → жёлтый, `OK` → ничего. Один RPC-оператор (`linkCrossChecked
  === false`) — `UNVERIFIED`, не `BLOCKED`. Адаптер: доля ≥ 0.1% supply и ≥ 20 отправок по
  endpoint'у — обычный маршрут, иначе «свежий адаптер» (жёлтый) с числами в причине;
- ошибка самого runner'а — `risk_unavailable`, жёлтая заметка, кнопку не держит; только
  «ещё читаем» (`risk_unknown`) держит как любой pending;
- маршруты вне покрытия (Solana, NTT, CCIP, и любой будущий не-EVM vm) оцениваются индикатором по
  собственным guard'ам вкладки (NTT с якорем со стороны источника и прошедшей симуляцией — зелёный,
  CCIP с пулом из TokenAdminRegistry — зелёный) — `riskCovers()` требует `vm === 'evm'` с обеих
  сторон, и восемь проверок там не показываются.

DVN сравниваются **по id оператора, а не по адресу** — на двух сетях у одного оператора разные адреса,
и сравнение по адресу помечало каждый здоровый маршрут как сломанный.

## Команды

```
npm test                 # check:whitelist + unit — то, что должно проходить всегда
npm run test:unit
npm run test:integration # живые публичные RPC, не входит в npm test, бывает флейки
npm run typecheck
npm run lint
npm run build            # обязан проходить после каждого этапа
npm run check:whitelist
npm run audit
```

Генераторы таблиц (`gen:` перезаписывает, `check:` только сверяет — годится для CI):

```
npm run gen:lz-v1    / npm run check:lz-v1     # lz-v1/chains.json из metadata LayerZero + RPC
npm run gen:lz-dvns  / npm run check:lz-dvns   # lz-risk/dvns.json
npm run headers                                 # заголовки для Cloudflare
```
